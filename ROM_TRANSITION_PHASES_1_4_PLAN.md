## Orchestrator contract

1. Start every subagent from the prepared branch tip. Own the protocol/identity registry, build pins, acceptance checklist, and cross-agent merges. Give agents nonoverlapping file ownership where possible. Merge a protocol or ROM-hook change before downstream agents rebase their parser/worker work.
2. Freeze a **versioned transition contract first**. An opaque, immutable emulator savestate is the authoritative restorable state; a decoded projection supplies legal actions, display data, assertions, and cache keys. A projection alone must never be used to reconstruct a deeper tree node. The state token must carry source, test ELF, worker/mGBA, protocol, critical policy, and save-format identity. 3. Define a decision boundary precisely: after entry/end-of-turn effects and any compulsory faint replacement have settled, immediately before the next player choice. 4. Maintain two execution modes in the same pinned test ELF: normal headless baseline and `SIDEDEX_LOGIC_ONLY`. Normal critical-hit behavior is required for parity tests and the future default planner. The existing `item-ability-only` critical policy may remain as an explicitly labeled alternate mode. Keep the mode/policy in request, result, and cache identities.
5. Preserve current four-card UI behavior during migration. Exact query cards should still publish when transition evaluation fails. Do not refine the current risk-first or follow-up heuristics except for a small correctness fix needed to keep them usable until phase 5.

## Phase 1 — fast, generic ROM transition engine

### 1A. Complete and restorable state

- Specify `DecisionState {state_blob_or_handle, identity, decoded_state, legal_player_actions, terminal}` and `TransitionResult {next_decision_state_or_terminal, trainer_action, compact_events, elapsed/frames}`. The decoded state must include both complete parties (HP, PP, status, item, mutable ability/form and battle data), active indices, stat stages, volatiles/disable/protect data, weather/terrain and their timers, side conditions, turn counters, trainer AI/item inventory, both RNG streams, and battle result. Record exact source fields and serialization rules for each; reject an unrepresentable field rather than silently defaulting it.
- Extend the worker from one `s_saved_state` slot to multiple immutable named blobs or bounded handles. Save at root and every deeper decision boundary; restore the same node repeatedly and branch to different player actions/seeds. Either make blobs portable across identical workers or explicitly implement transfer/reconstruction before phase 3. Test A→B→restore A→C and repeated same-seed A→B byte-for-byte equivalence.
- Replace the startup-only fixture assumption. Root creation may still use the existing mailbox/party builder, but deeper transitions consume saved decision states directly; remove the one-replay dependency from the transition path. Keep schema-v2 UI snapshots as inputs to root construction, without claiming arbitrary manual midbattle edits are supported until every required field maps.
- Fix trainer item execution in the **resolved** turn while retaining the real ROM AI. The current query-only item prediction and item-agnostic recommendation are insufficient for MCTS. Include switch-in effects, faint transitions, and terminal state as explicit cases. No Python battle-mechanic substitute.

### 1B. Logic-only execution and script pump

- Add `SIDEDEX_LOGIC_ONLY` only to the test build and a runtime mode switch at the fixture boundary. Audit controller commands and frame waits as pure presentation, stateful presentation, or game logic. Instantly acknowledge only proven pure-presentation requests; execute any stateful part synchronously before acknowledgement. Keep normal headless mode as the differential baseline in the same source revision.
- Add a bounded battle-script pump after presentation waits are removed. It may run successive synchronous commands in one callback until a genuine asynchronous mechanical dependency, an unskippable controller command, a decision/terminal boundary, or an instruction budget. Yield safely on budget exhaustion; surface a structured budget failure rather than spinning to the frame cap.
- Capture a choice-point savestate after all entry mechanics and before player/AI choice. For each transition: restore state → inject RNG → inject validated player action → let real trainer AI act → run logic-only turn → settle forced follow-ups → export next state. Verify no player-action leakage into trainer AI by running different player actions with the same pre-choice state/RNG and comparing the AI's pre-reveal choice where game rules say it must be independent.

**Phase-1 gate:** A deterministic root and at least one deeper nonterminal node can branch repeatedly; terminal/faint/switch/item cases finish without a 24,000-frame fallback; complete state and both RNG streams are returned; normal mode remains executable. Record median/p95 transition latency, frames, save/restore time, and state size. Do not promise the report's 3–20 ms stretch target before measuring.

## Phase 2 — split exact queries from transitions

- Introduce explicit operation types `QUERY_DAMAGE`, `QUERY_AI_ACTION`, and `SIMULATE_TURN`, each accepting a decision-state token (root or deeper node) and returning a versioned result. Queries must leave the source token immutable and must not resolve a turn. `SIMULATE_TURN` returns the complete phase-1 result without recommendation policy or UI card formatting.
- Reuse the existing query hook/parser where correct. `QUERY_DAMAGE` returns engine-derived damage distribution/range, accuracy, crit behavior, and immediate KO probability, with explicit unsupported reasons. The present Python `rom_query._multi_hit_probability` applies hit-count and Sash/Sturdy mechanics; move that mechanic-dependent composition into the ROM query layer (or have the ROM enumerate complete outcome weights and leave only generic integer aggregation to Python) to satisfy the ROM-authoritative boundary. Do not silently relabel an unsupported case `engine-exact`.
- `QUERY_AI_ACTION` runs the actual trainer AI once for the supplied state/RNG and returns its action without turn resolution. Keep a fixed-seed preview distinct from a probability distribution. Ensure item decisions are neither consumed nor repeated by a subsequent transition from the same immutable state.
- Adapt `rom_eval.evaluate` to call query operations and preserve/publish their cards independently of transition failures. Keep current UI card names and explicit critical-policy labels. Record p50/p95 query latency separately from transition latency.

**Phase-2 gate:** Same state + seed gives stable query results; query does not change saved state/RNG; query card availability does not depend on rollout completion; supported single-hit and multi-hit fixtures match normal engine outcomes or documented exact enumeration. Unsupported mechanics fail closed.

## Phase 3 — parallel rollout infrastructure

- Reuse `EnginePool(size=3)` but change `evaluate`/the new adapter so independent transition jobs are dispatched to all available workers for one request. The current `with _engine_session(...)` around the whole seed loop serializes all work on one worker. Use a planner-agnostic queue keyed by request, node, action, and paired seed; merge results in deterministic order. A worker may execute a bounded local batch, but a long trajectory must not block all workers.
- Preserve common-random-number pairing: the same root RNG pair is used for every candidate action, and a sample is counted as paired only when every required action completed. Return completed partial work on deadline/cancellation, never invented zero outcomes. Keep exact query cards published independently. Include bounded retries only for idempotent jobs after worker failure; prevent duplicate counts.
- Evolve today's JSONL `batch_turns` (hex mailbox payloads, textual `ROMTRACE` replies, max eight) to a versioned binary/EWRAM input and compact binary state/result buffer. Retain trace mode for diagnostics and differential tests. Measure whether worker process I/O, emulator frames, state serialization, or Python scheduling dominates before tuning batch size. Avoid designing around the current recommendation payload.
- Support portable state blobs or a scheduler rule that routes a node to the worker holding its state; document the cost of moving/evicting states. Add limits for queued jobs, worker memory, per-job frames/instructions, deadline, and output size. Extend cache keys to include source/ELF/worker/mGBA, wire/state format, mode, critical policy, and future planner identity; do not cache opaque worker-local handles across process restarts.

**Phase-3 gate:** A request demonstrably uses all three workers, gives the same paired results as one-worker execution, survives one worker exit without duplicating observations, respects deadlines, and improves aggregate *verified transitions per second* on the benchmark scenarios. Report per-worker and pool throughput plus p50/p95 latency and IPC bytes.

## Phase 4 — equivalence and release-ROM validation

- Build a fixed-seed fixture matrix that covers physical/special damage, accuracy miss, normal and forced critical hits, priority/speed ties, status/volatile effects, abilities, held/trainer items, weather/terrain, hazards and other side conditions, switches and switch-in effects, faint/forced replacement, terminal win/loss, and multiple-turn branches. Include smart-AI bosses and the first-turn KO regression. Freeze input state and both RNG streams for every comparison.
- For each fixture, run **normal test ELF** and **logic-only test ELF** from the same decision checkpoint. Compare trainer action, all decoded state fields named in phase 1, terminal/decision boundary, ordered mechanical events, and final values of both RNG streams. Include raw/opaque state comparison where deterministic serializer metadata permits; explain any benign presentation-byte differences. A mismatch is a failure, not an ignored timing artifact.
- Add an AI leakage test with multiple player actions and identical pre-choice seed; verify the trainer decision follows the intended ROM information boundary. Test restore determinism and state-token identity rejection across ELF/worker/protocol/policy changes.
- Build a release-ROM differential harness for representable fixed-seed states using the pinned `pokeemerald.gba`. Compare the test ELF's **normal-critical, normal-logic** path with the release ROM's observable battle action/state/RNG projection. The existing test-only mailbox cannot be assumed to exist in the release ROM; the harness needs an explicit setup/observation method and a documented mapping of test-fixture state to real ROM state. Run representative scenarios before calling any result ROM-verified. A failed/unavailable comparison leaves the product labeled compiled-engine, as it is today.
- Pin the exact source diff, rebuilt ELF, worker, release ROM, protocol/state schema, mode, and policy used for evidence. Make verification reproducible without checking generated ROM/ELF files into Git. Run focused worker/query/transition tests, full suite, `app.py --self-check`, and a manual four-card UI walkthrough after integration.

**Phase-4 gate:** Zero unexplained normal-vs-logic-only state/action/RNG differences in the accepted fixture matrix; release-ROM fixed-seed comparisons pass for the claimed coverage; performance numbers are measured on the verified path. If release comparison is not ready, phases 1–3 may be integrated, but phase 4 remains open and no ROM-verification claim is made.
